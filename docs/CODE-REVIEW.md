# 流程自查（2026-10-20）

代码版本：0.2.1。当前结论是可继续编写部署手册，真实多用户验收尚未完成。

| 用户操作 | 代码行为与检查 |
| --- | --- |
| 新企业部署 | 先创建空飞书应用取得应用凭据，再部署 AWS 应用取得 HTTPS 地址，配置 OIDC 客户端和两个回调，启用登录；首位管理员通过一次性登记链接固定飞书企业。 |
| 同企业员工进入 | 后端 tenant 模式验证实际飞书用户所属企业；飞书应用发布范围另外控制哪些员工可以使用入口。 |
| 首次登录报表账号 | 验证 OIDC 签名、issuer、audience、nonce、state、PKCE；仅使用明确验证过的邮箱匹配指定 namespace 中唯一有效的 QuickSight 用户。 |
| 自动关联 | 原子保存 issuer/sub 与 QuickSight 用户的关联及反向归属锁；相同邮箱的另一个登录身份不能覆盖既有关联。已有手工关联优先。 |
| 再次登录 | 复用关联；检查账号仍然有效。自动关联还检查邮箱、PrincipalId 和关联策略是否一致。 |
| 查看报表 | 使用关联的 QuickSight UserArn 查询权限，每次生成嵌入链接前重新核对所选仪表盘。 |
| 切换账号 | 清除应用内旧身份与报表，重新完成所选登录系统的认证；不读取其他 Chrome 标签页中的 QuickSight 登录状态。 |
| 推广给全员 | 在同企业 tenant 模式下，符合自动关联条件的新员工不需要改代码或重新部署；需具备登录账号、已有 QuickSight 用户及报表授权，并在飞书发布范围内。 |

## 本次修复

- 原有手工关联只在首次创建时检查 QuickSight 用户是否有效；现在存量会话及再次登录也检查。新手工关联同时记录 PrincipalId，防止同名重建用户沿用旧授权。
- 停用某个登录配置后，旧会话不再通过报表接口认证。
- 两项新增回归测试覆盖停用账号、重建账号和停用登录配置。

## 文档必须说清楚的边界

- 仅在 Cognito 新增用户不等于开通 QuickSight：自动关联需要已有且唯一匹配的 QuickSight 用户。程序不自动创建付费用户，不自动授予报表权限。
- 当前报表会话固定为 1 小时，到期重新发起登录；是否需要再次输入密码取决于登录系统的会话。没有自动刷新 OIDC 会话。
- 应用退出不等于退出全部企业 SSO；切换账号单独触发重新认证。
- 已发出的 QuickSight 嵌入会话有自己的生命周期；后端拒绝新请求不代表立即撤销已经打开的嵌入会话。
- 历史手工关联未记录 PrincipalId 的条目保留兼容，仍按原 ARN、subject 和有效状态验证；不能声称这些旧条目具备新关联的同名重建检测。
- 当前匿名访问未实现。邮箱变更、重复邮箱、缺少验证、用户删除重建或关联策略变更需要管理员处理，系统不会猜测或静默换绑。
- 自动关联策略包括 issuer、AWS 账户、区域、namespace 与允许邮箱域；改变策略会使旧自动关联失效，需要受控迁移。正常新增员工不属于改变策略。

## 尚待真实验收

新员工首次登录及两名员工权限隔离、飞书手机 WebView、企业 Keycloak、全新 AWS 账户部署。现有自动化及模拟 UI 测试不能替代这些验收。
